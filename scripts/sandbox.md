# Песочница

Одноразовый набор выдуманных баз знаний и рабочих копий, на котором панель можно ломать, не задевая
живые базы и профиль оператора. Собирается под задачу, которую принимают: в песочницу кладутся только
куски, названные при сборке, и свой кусок задачи, если нужного ей случая в готовых нет. Пересобирается
той же командой с нуля: что бы в песочнице ни испортили, откат ничего не стоит.

```powershell
pwsh -NoProfile -File scripts/sandbox.ps1 -Pieces house,quirks
pwsh -NoProfile -File "$env:LOCALAPPDATA\agents-kit-web\sandboxes\<копия>\start-panel.ps1"
```

Первая команда собирает каталог песочницы и печатает всё, что нужно дальше: адрес панели, пути к файлам
режимов и команду пересборки с теми же ключами. Вторая поднимает панель — интерфейс, а API рядом, на
следующем порту; гасятся оба вместе по Ctrl+C. Без кусков сборка ничего не трогает и перечисляет, какие
куски бывают.

Панель на песочнице живых баз не видит вовсе: список баз, реестр живых сессий, профиль Claude Code,
журналы расхода, ключ доступа, отметку о поставленной панели и модель голосового ввода она берёт из каталога
песочницы, а не из профиля оператора. «Расход» в песочнице пуст, а проценты лимита не читаются — ключа доступа нет.
Модели голосового ввода в свежей песочнице нет: «Установить» в «Настройках» качает её в каталог песочницы, и
«Удалить» живую модель не трогает.

## Своя песочница у каждой копии

Каталог песочницы — `%LOCALAPPDATA%\agents-kit-web\sandboxes\<имя рабочей копии>`, целиком вне репозитория
панели и вне баз знаний. Порт закреплён за каталогом песочницы в `sandboxes\ports.json`: первой песочнице
достаётся 5100, следующей 5102 и так далее — занятые порты пропускаются, — и от сборки к сборке он тот же.
Своя песочница с ключом `-Root` получает свой порт. Копия с тем же именем, но из другого места, получает
каталог с коротким хвостом из хэша своего пути. Сборка из соседней копии чужую песочницу не трогает: на ней
может идти чужая приёмка. Порты песочниц не пересекаются ни с поставленной панелью (5080), ни с dev-запуском
(5173 и 5078).

Прежний общий каталог `%LOCALAPPDATA%\agents-kit-web\sandbox` сборка больше не трогает; когда ни одна копия
не собирает песочницу прежним скриптом, его можно удалить руками.

Базы и копии в песочнице — настоящие git-репозитории: список копий панель берёт из `git worktree list`.

Базы песочницы разложены, как база кита формата 8: копии этой машины и её оператор — `local\me.json`, личный
репозиторий оператора `local\me` со своим git — флоу, исполнители, `backlog.md`, память задач `work\<машина>\<файл>.md`
с флоу задачи рядом — `work\<машина>\<файл>\flow\`, копией сценария «мелкий», по которой задача идёт, — и их
`artifacts\`, папка оператора `people\sandbox` — выложенное для коллег: в ней лежит только каркас пустого
флоу, как его кладёт кит, и панель её не читает. Оператор песочницы — `sandbox`,
машина — имя этого компьютера, как его пишет кит.

## Куски

| Кусок | Что в нём |
|---|---|
| `house` | здоровый проект «Дом»: три копии, память с тремя вопросами, живые сессии |
| `orders` | проект «Заказы» со своими буквами номеров |
| `tracker` | проекты с трекером: GitHub и YouTrack с задачами на оператора, YouTrack без ключа и без проекта, описание трекера без строк и Jira; у GitHub в копии идёт задача из трекера |
| `no-product` | база без описания проекта |
| `broken-json` | база с битым `agents-kit.json` |
| `old-format` | база прежнего формата кита (5) — панель её не читает |
| `new-format` | база нового формата кита (формат панели + 1) — панель её показывает с предупреждением и не правит |
| `stages-only` | база с этапами без сценариев |
| `no-flow` | база без этапов и сценариев |
| `quirks` | «Кривые копии»: кривые копии и памяти, файл мёртвой сессии, лишний исполнитель |
| `broken-kit` | кит без скриптов |
| `load` | база на полсотни копий — панель под опросом; собирается долго |

Куски друг от друга не зависят: каждый заводит свои базы и копии. Кит и агент подменены заглушками
в любой песочнице.

**Здоровый проект — `house`.** База «Дом» с описанием, флоу, бэклогом и тремя копиями: `house` свободна, в
`house-task` идёт задача B-7 флоу «мелкий» с тремя вопросами оператору без ответа — с рекомендованным вариантом, с вариантами без рекомендованного и без вариантов, а `house-done` — копия, где задача уже
закончилась. Проверки кита отвечают «всё в порядке», подставной агент — как при удачной работе. На этом
наборе проверяется обычная работа панели: ответить на вопрос, поправить флоу, добавить запись в бэклог,
завести копию, запустить задачу.

Запуск задачи из панели заводит в песочнице живую сессию-пустышку, как настоящий агент: копия сразу
числится занятой со статусом «Запускается», а памяти задачи у неё так и не появится — подставной агент
её не пишет.

В `house-done` стоит отработавшая сессия задачи — такую панель гасит сама, и других сессий в этой копии
нет, чтобы её строку ни с чем не спутать. Ждёт она этого секунды, а не минуты: выдержку и срок опроса
задаёт строка запуска панели. Через полминуты после подъёма строка «Дом · house-done» уходит из раздела
«Сессии», а её пустышка гаснет. В `house` при этом остаётся своя работающая сессия, и её панель не
трогает.

**Свои буквы номеров — `orders`.** База «Заказы» нумерует записи буквами «ORD», а не «B»: номер панель узнаёт
по буквам проекта из счётчика бэклога. В бэклоге рядом с записями ORD-… стоит запись чужими буквами
B-7 — номер у неё виден, а «Взять задачу» погашена, пока кит её не перенумерует, — и запись без номера.
Копий три: `orders` свободна, в `orders-export` идёт задача ORD-12 — номер стоит в колонке «№», —
а в `orders-utf` задача не из бэклога, чей заголовок начат словом «UTF-8»: номером оно не становится.
У ORD-12 в памяти раздел «Артефакты» — макет ссылкой, снимок файлом в `artifacts\` личного репозитория (путь
от его корня, как пишет кит) и спецификация прежним полным путём: окно ответа показывает их блоком «Артефакты», и щелчок
по пути открывает файл в VS Code. Файл спецификации лежит в `files\` песочницы, вне копии. У записи ORD-14
бэклога свои «Артефакты» — образец выгрузки в `artifacts\` личного репозитория и ссылка: окно записи показывает их блоком
под описанием. У `orders-utf` макет записан по-старому, подразделом «Дизайн» критериев: окно его
не показывает ни артефактом, ни критерием.
Подставной агент записи в бэклог берёт буквы из того же счётчика.

**Трекер — `tracker`.** Трекер каждой базы куска описан строками «трекер:», «сервер:», «проект:» в начале раздела
«Где задачи» `tracker.md`, как у кита с формата 7. У базы «Трекер» — GitHub, репозиторий `sandbox/tracker`: раздел
«Бэклог» под её записями показывает группу задач GitHub, назначенных на оператора, — три задачи, ссылками на GitHub,
у каждой «Взять задачу» в свободную копию `tracker`. Задачи отдаёт подставная `gh` — в каталоге `gh-bin` песочницы,
впереди PATH всегда, и с `-RealAgent` тоже: настоящая `gh` пошла бы в GitHub под аккаунтом оператора. Задачи лежат
в `gh-issues.json` корня песочницы, объектом «репозиторий: [задачи]», — их можно править на ходу; репозиторий, которого
там нет, подставная `gh` называет несуществующим, как GitHub.

У базы «YouTrack» — YouTrack, проект `ABC` на подставном сервере YouTrack песочницы: `youtrack-stub.ps1` корня
песочницы, его поднимает `start-panel.ps1` рядом с API на порту песочницы плюс 1000 (адрес печатает сборка). Задачи
YouTrack панель читает сама, по ключу из «Настроек»: пока ключа нет, на месте задач — «нет ключа». Ключ сервер
принимает один — `perm:sandbox`: его вводят в «Настройках», в карточке «Серверы трекеров», с адресом сервера; другой
ключ сервер отклоняет, и карточка его не сохраняет. Список серверов с ключами панель песочницы держит в `trackers.json`
рядом со своим `bases.json` — ключей оператора она не видит. С ключом группа показывает четыре задачи с номерами разной
длины и «Взять задачу» в свободную копию `tracker-youtrack`. Задачи лежат в `youtrack-issues.json`, объектом
«проект: [задачи]». У базы «YouTrack без ключа» сервер другой (путь `/other`), ключа к нему нет; у «YouTrack без
проекта» проект `ZZZ`, которого на сервере нет; у «Трекер без строк» трекер описан словами, без строк; у «Трекер Jira» —
Jira, её панель не читает: задач у них нет, и панель говорит почему.
Отбор задач строкой «фильтр:» описания (B-300) задают в «Настройках», в поле «Фильтр» окна трекера. Подставная `gh`
понимает в нём `label:метка`, `milestone:этап` и слова заголовка; непонятное, как у GitHub, ничего не находит, а не
отвергается; у задач «Трекера» метки `bug`, `enhancement`, `installer` и этап `v2` у #52. Подставной YouTrack понимает поля
`State` и `tag` — значением или `{значениями}` через запятую — и слова заголовка, другое поле отвергает («Unknown field»);
у задач «YouTrack» состояния `To Do` (ABC-7, ABC-104) и `In Progress`, теги `почта` и `отчёты`. Фильтр `State: Done`
ничего не находит — на нём видна серая строка «Бэклога» о пустом отборе.
Записи базы «Трекер» переносятся в трекер кнопкой «В трекер» или просьбой к Чудо-Юдо «перенеси B-1 в трекер»: подставная
`gh` дописывает задачу в `gh-issues.json` следующим номером — раздел перечитывает трекер, и она сразу видна в группе задач, — а описание,
которое ушло в задачу, кладёт в `gh-created\<номер>.md` корня песочницы. У записи B-3 приложен файл и ссылка: окно
переноса называет файл, который в задачу не попадёт. Режимы `gh-mode.txt` ломают и заведение задачи. Записи базы
«YouTrack» переносятся так же — в YouTrack: подставной сервер дописывает задачу в `youtrack-issues.json` следующим
номером, описание кладёт в `youtrack-created\<номер>.md`, а режимы `youtrack-mode.txt` ломают и заведение. У «Трекера
без строк» и «Трекера Jira» кнопки «В трекер» нет.

Описания трекеров всех баз видны в «Настройках», в карточке «Трекеры проектов» (B-293). У «Трекера» в копии
`tracker-gh-48` идёт задача «GitHub #48» из его трекера: «Удалить» погашено и называет копию, а «Взять задачу» у #48
в «Бэклоге» погашено. У «Дома» (кусок `house`) трекера нет — на нём видно «Завести». Запись описания проверяет трекер
теми же подставными `gh` и сервером YouTrack, пишет `tracker.md` в git базы и сводит базу заглушкой `sync.ps1` кита —
сервера у баз песочницы нет, заглушка только отвечает по `sync-mode.txt` и пишет вызовы в `sync.log` у скриптов кита.
У баз без копий («YouTrack без ключа» и прочих) записать описание нельзя: скрипту кита не из чего свести базу.

**Разговор о бэклоге.** Подставной агент бэклога отвечает по словам просьбы. Просьба без слов «удали»,
«измени», «поправь», «объедини» — новая запись: он дописывает её и коммитит в личный репозиторий. «Удали ORD-3» предлагает
удалить запись, «измени ORD-3» или «поправь» — дописывает к её заголовку «(изменено)», «объедини ORD-3 и
ORD-5» — вторую в первую; в файл он их не пишет, пишет панель по «Сохранить». Такое же слово без номера —
вопрос «та ли это запись» про первую запись бэклога, а «да» в ответ делает с ней прежнюю просьбу.

**Исполнители.** Они лежат в личном репозитории оператора: у каждой базы песочницы в его истории есть `reviewer`
и `doc-writer` в `local\me\agents` — их и зовёт её флоу. В «Кривых копиях» (`quirks`) рядом лежит ещё `spec-writer`, заведённый
«оператором» прямо в личном репозитории и мимо панели: в разделе «Исполнители» он виден наравне с остальными. По копиям исполнителей развозит сама панель, прогоном заглушки кита: делать для
этого ничего не нужно, и в панели про перенос ничего не сказано.

**Флоу** у баз песочницы в форме кита, в личном репозитории `local\me`: сценарии в `flow\scenarios.md` и этапы
по файлу в `flow\stages`.
Сценариев два — «полный» и «мелкий» из общих этапов, с разными возвратами у «Приёмки»: на них видно, что
этап правится один раз для всех сценариев, а возвраты у каждого сценария свои. У возврата «Ревью»
в «полном» стоит предел кругов 2, у возврата «Приёмки» предела нет — видны оба случая.
По «мелкому» идут задачи в работе, и он правится, переименовывается и удаляется, как любой: каждая задача
идёт по своей копии сценария рядом с памятью, и таблица копий показывает её этап и после правки.

Этап «Сборка» в сценарии «полный» нарочно зовёт `builder`, которого нет ни в одной базе. На ней видно,
как панель запирает запись: этап помечен, в полосе внизу раздела названа причина, а кнопка
«Сохранить» погашена, пока имя не заменили заведённым.

Две базы без копий показывают пустые состояния раздела «Флоу»: `stages-only` — этапы есть, списка
сценариев нет, `no-flow` — нет ни этапов, ни сценариев.

## Свой кусок задачи

Случай, которого нет ни в одном готовом куске, сессия задачи дописывает сама — скриптом PowerShell
вне кода панели, например во временном каталоге своей сессии, — и называет его ключом `-TaskPiece`.
Кусок внутри рабочей копии сборка не берёт: он уехал бы в коммит ветки.
В код панели свой кусок не попадает; его копия остаётся в песочнице — `task-piece.ps1`, — и по ней
видно, из чего песочница собрана.

Скрипт выполняется после названных кусков в той же области, что и сборка. Ему видны:

- кирпичи `fixtures.ps1` — `New-Repo`, `Add-Commit`, `Write-Utf8`, `Write-Json`, `Start-Dummy`, `Write-Session`;
- функции баз `sandbox.ps1` — `New-Base` (ключ `-Format 5` — база до перевода на формат 6), `New-Memory`, `New-Flow`, `New-Backlog`, `New-Agents`, и адреса
  раскладки базы — `Get-Personal` (личный репозиторий), `Get-MemoryDir` (память копий этой машины),
  `Get-OperatorDir` (папка оператора, выложенное): `New-Flow`, `New-Agents` и `New-Backlog` берут личный
  репозиторий, `New-Memory` — путь файла в каталоге памяти; память по-старому, в `<база>\work`, панель не увидит;
- каталоги `$Root`, `$basesDir`, `$copiesDir`, `$sessionsDir`, `$claudeDir`, `$panelDir`, `$projectsDir`
  (журналы расхода) и `$kitDir` (заглушка кита);
- списки, куда кусок дописывает своё: `$bases` — базы в списке панели, `$links` — связь копий с базами
  для заглушки кита, `$findings` — находки сверки по базе, `$dummies` — номера пустышек сессий.

Переменные сборки кусок только читает: переназначенный `$Root` или `$bases = @(...)` вместо `$bases.Add`
ломает то, что сборка делает после куска. `exit` в куске обрывает сборку без `start-panel.ps1`. `$PSScriptRoot`
в куске — каталог песочницы, где лежит его копия, а не место, откуда его взяли: соседние файлы куску
передаются полными путями.

```powershell
$copy = Join-Path $copiesDir 'shop'
New-Repo $copy
Write-Utf8 (Join-Path $copy 'README.md') "# Магазин`n"
Add-Commit $copy 'Первый коммит'
$base = Join-Path $basesDir 'shop-knowledge'
New-Base $base 'Магазин' @($copy)
# Память задачи — в личном репозитории, в каталоге этой машины, и коммитится в его git.
New-Memory (Join-Path (Get-MemoryDir $base) 'shop.md') $copy 'main'
Add-Commit (Get-Personal $base) 'Память задачи'
$bases.Add($base)
$links.Add([pscustomobject]@{ path = $copy; status = 'Linked'; base = $base })
$findings.Add([pscustomobject]@{ base = $base; findings = @() })
```

## Как ломать

Кит и агент подменены заглушками: настоящий кит полез бы в живую сверку и завёл бы настоящую копию, а
настоящий агент стоит денег и прав. Заглушки отвечают и здорово, и криво; режим — в файлах корня
песочницы, они читаются на каждый вызов, и панель для смены режима перезапускать не нужно.

`kit-mode.txt`:

| Режим | Что увидит панель |
|---|---|
| `ok` | находки базы как заданы при сборке |
| `empty` | «ответ скрипта кита не разобран» |
| `garbage` | то же — в потоке не JSON |
| `huge` | четыре тысячи находок |
| `fail` | текст ошибки кита |
| `hang` | «проверка кита не уложилась по времени» |

`claude-mode.txt`:

| Режим | Что увидит панель |
|---|---|
| `ok` | ход работы строками и ответ |
| `garbage` | «Агент завершился без ответа» и мусор в выводе |
| `truncated` | пара строк хода, итога нет |
| `slow` | тот же ответ, но по строке раз в несколько секунд |
| `fail` | ненулевой код и текст отказа |

`gh-mode.txt` — подставная `gh`, задачи трекера в разделе «Бэклог»:

| Режим | Что увидит панель |
|---|---|
| `ok` | задачи из `gh-issues.json` |
| `login` | «Программа gh не вошла в аккаунт GitHub» |
| `error` | «GitHub ответил ошибкой: HTTP 502…» |
| `slow` | те же задачи через несколько секунд — заготовка на месте группы |

Программу `gh`, которой нет вовсе, песочница не показывает: подставная стоит впереди PATH.

`youtrack-mode.txt` — подставной сервер YouTrack, задачи YouTrack и проверка ключа в «Настройках»:

| Режим | Что увидит панель |
|---|---|
| `ok` | задачи из `youtrack-issues.json`; ключ `perm:sandbox` принят |
| `rejected` | «Сервер … отклонил ключ» в «Бэклоге», отказ сохранить ключ в «Настройках» |
| `error` | «YouTrack ответил ошибкой: Сервер песочницы на обслуживании» |
| `slow` | ответ через двадцать секунд — панель не дожидается и пишет, что сервер не ответил |
| `slow-create` | задачи читаются как в `ok`, а заведение задачи (перенос записи) отвечает через семьдесят секунд — задача заводится, панель не дожидается и пишет, что задача, возможно, заведена |

`sync-mode.txt` — заглушка сведения базы с сервером, запись и удаление описания трекера в «Настройках»:

| Режим | Что увидит панель |
|---|---|
| `ok` | описание записано, база «отправлена» |
| `push-fail` | описание записано, окно говорит, что база на сервер не ушла, и показывает слова кита |
| `pull-fail` | базу не забрать с сервера — описание не записано, окно показывает слова кита |
| `offline` | сервер недоступен: описание записано на этом компьютере, окно говорит, что на сервер не ушло |

Рядом со справкой о флоу в заглушке лежит справка о раскладке базы — копия `reference\base-layout.md` установленного
кита: из её раздела «Трекер» панель подаёт правила описания трекера Чудо-Юдо в окне «Трекер проекта». Переписка с
подставным агентом: на первую реплику он переспрашивает, на вторую предлагает описание целиком — пустое заводит
GitHub-трекером `sandbox/tracker`, имеющееся дополняет разделом «Взятие задачи» словами просьбы. Реплика со словом
«неполное» — и первой тоже — даёт описание с пустым разделом «Задача закрыта»: панель возвращает ответ на доработку,
и агент дописывает его.

В заглушке кита лежит справка о флоу установленного кита — копия `reference\flow-stages.md`, путь к
киту берётся из списка баз оператора. Из неё панель подаёт агенту правила формы сценария и этапа, и «Переписать с
Чудо-Юдо» в разделе «Флоу» в песочнице не отвечает отказом. Кита не нашлось — в заглушке короткая своя справка.
Переписка «Переписать с Чудо-Юдо» с подставным агентом: на первую реплику он переспрашивает, на вторую предлагает
правки — дописывает к выходу первого этапа слова просьбы, заводит этап «Заметки подставного агента» и ставит его
в конец первого сценария; дальше отвечает словами, а по слову «удали» убирает этап заметок. Реплика со словом
«неполный» — в любой момент, и первой тоже — заводит этап «Черновик подставного агента» без выхода: панель сама
возвращает ответ на доработку, и агент дописывает выход. Со словами «неполный дважды» он и дописанный ответ шлёт
без выхода, и панель показывает ошибку. Черновик заводится новым этапом, поэтому второй раз за переписку панель
отклонит его как повтор названия — для нового случая начинают новую переписку. Настоящий агент — ключом `-RealAgent`.

Сверка баз идёт в фоне раз в полминуты, и снимок меняется, когда круг по всем базам пройден; кнопка
«Проверить сейчас» его торопит. В режиме `hang` круг занимает минут восемь — это собственный срок
ожидания панели, помноженный на число баз.

## Ключи

| Ключ | Что делает |
|---|---|
| `-Pieces <куски>` | куски песочницы через запятую — таблица «Куски» |
| `-TaskPiece <путь>` | свой кусок задачи — раздел «Свой кусок задачи» |
| `-Root <путь>` | другой каталог песочницы |
| `-Port <номер>` | другой порт панели; API берёт следующий за ним |
| `-RealAgent` | не подменять агента: панель зовёт настоящий `claude` (деньги и настоящие права) |
| `-NoSessions` | не поднимать процессы-пустышки под живые сессии агентов куска `house` |
| `-Verify` | ничего не собирать, а сверить живое состояние со снимком, снятым при сборке |
| `-UpdateKit` | ничего не собирать, а выпустить новую версию плагина кита: следующий номер рядом с прежним, запись плагина переписана |
| `-UpdateKit -DropOldKit` | то же, и папка прежней версии удалена, как это иногда делает обновление плагина |

Кит песочницы стоит плагином Claude Code, как его ставит установщик: `claude\plugins\cache\agents-kit\agents-kit\1.14.2`
и запись в `claude\plugins\installed_plugins.json`. `-UpdateKit` на собранной песочнице — обновление плагина: панель
замечает новую версию, не перезапускаясь, и предлагает перейти на неё в «Настройках»; «Проблемы баз» говорят о ней
со следующим кругом сверки.

`-Verify` отвечает на главный вопрос после сеанса: не изменилось ли что-то живое. Он сверяет список
отслеживаемых баз оператора и каждую живую базу — её последний коммит и незакоммиченные правки.
Расхождение он называет пофайлово: живые базы меняют и сессии агентов в других рабочих копиях, и по
имени файла видно, чья это работа.

## Чего песочница не делает

- Не проверяет, правильно ли панель зовёт настоящего агента — с какими ключами, что уходит ему в ввод,
  какие права даются. Это проверяется точечно и только на клоне базы.
- Не заменяет тесты: своих проверок у скриптов в проекте нет, песочница — для ручных проб.
- Не чинит найденное. Замеченное в ней уходит записью в бэклог базы знаний.

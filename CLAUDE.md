# agents-kit-web

Веб-панель оператора над базами знаний agents-kit.

## Структура

- `backend/` — .NET 10 minimal API (`AgentsKitWeb.slnx`): `src/AgentsKitWeb.Api`, тесты в `tests/AgentsKitWeb.Api.Tests`.
- `frontend/` — React + TypeScript на Vite. Фронт ходит на относительный `/api`, dev-сервер Vite проксирует его на API.
- `design/` — временный набросок, не спецификация.

## Руководство

Раздел «Руководство» панели — страницы в `frontend/src/guide/`, по странице на раздел, плюс «С чего начать» и «Шапка
панели»; оглавление — `frontend/src/guidePages.ts`. По ним же отвечает Чудо-Юдо, когда оператор спрашивает о панели.
Задача, которая меняет вид или поведение раздела панели — кнопки, окна, надписи, статусы, что можно и чего нельзя, —
правит в той же ветке и его страницу руководства: руководство описывает панель такой, какая она уходит в dev.

## Запуск

```sh
# API на http://localhost:5078
dotnet run --project backend/src/AgentsKitWeb.Api --launch-profile http

# фронт на http://localhost:5173
cd frontend
npm install
npm run dev
```

## Номер версии

Номер версии панели — четыре числа 0.X.Y.N. В `version.txt` лежит номер выпуска 0.X.Y, а номер сборки Беты N
подставляет сборка на GitHub: Беты одного выпуска идут подряд — 0.28.1.1, 0.28.1.2, 0.28.1.3. Пока панель
в разработке, первое число не трогается: выпуск ломает привычное — X, в нём новое или починки — Y; после поднятого X
число Y — ноль.

Номер выпуска поднимает агент в ветке задачи своим коммитом перед слиянием в dev, но не на каждое слияние. Первая
задача после выкладки в Стабильный поднимает его на один шаг — X или Y. Следующие задачи номер не трогают, кроме
одного случая: поднято одно Y, а задача ломает привычное, — тогда X. Последняя выкладка в Стабильный — наибольший
тег `v<номер>` без `-dev`; перед слиянием подтяни теги (`git fetch origin`). До 0.28.1 номер поднимался на каждое
слияние и был из четырёх чисел в самом `version.txt`; выпуски обеих записей панель и скрипты видят рядом.

Номер, поднятый не по правилу, ловят хуки git из `.githooks`: слияние в dev не проходит, если номер выпуска поднят
не так, как велит последний Стабильный, а отправка dev и master — если номер ниже, чем уже лежит на сервере. Хуки
слияния git зовёт, только когда создаёт коммит слияния, поэтому слияние в dev настроено всегда его создавать;
`--ff-only` в команде, которым dev подтягивают к серверу, эту настройку перебивает. Обе настройки включаются один раз
на клон и действуют во всех его рабочих копиях:

```sh
git config core.hooksPath .githooks
git config branch.dev.mergeOptions --no-ff
```

Хуки каждая копия берёт из своей выкачанной ветки: в копии на ветке, отрезанной раньше, чем в dev появился
`.githooks`, их нет, пока она не подтянет dev.

## Поставленная панель

Для постоянной работы панель ставится готовой сборкой с GitHub и работает на http://localhost:5080 — отдельно
от dev-запуска. Бету выпускает `.github/workflows/release.yml` на каждый приход кода в dev — предварительный выпуск
`v<номер>-dev` со следующим номером сборки. В Стабильный — выпуск `v<номер>` — уходит только признанная оператором Бета:
кнопка «Выпустить в Стабильный» в карточке «Панель» у поставленной Беты запускает `.github/workflows/promote.yml`,
и тот выпускает ту же сборку с тем же номером и переносит master на её код. Иначе код в master не приходит: агент
master не трогает, поломку в Стабильном чинят обычной задачей через dev. Архив — панель со средой .NET внутри,
собранный фронт в `wwwroot`, `build.json` о сборке и скрипты `deploy.ps1` и `update.ps1`. Перечень задач выпуска
считает `scripts/release-notes.ps1`.

Кнопка «Обновить» в «Настройках» запускает `update.ps1` из своей сборки: он скачивает выпуск канала и ставит его
`deploy.ps1` — останавливает панель, подменяет каталог `%LOCALAPPDATA%\agents-kit-web\app`, регистрирует или обновляет
задачу Планировщика заданий `agents-kit-web panel` (при входе текущего пользователя, без прав администратора)
и запускает панель. Панель читает тот же `bases.json` из `%APPDATA%\agents-kit-web`, что и dev-API.

Собрать и поставить панель из исходников — для разработки и приёмки ветки:

```powershell
pwsh -NoProfile -File scripts/publish.ps1
```

Скрипт собирает master (или `-Ref`) во временном git worktree тем же `scripts/build.ps1`, что и выпуск, — рабочая копия
и её ветка не трогаются, — и ставит через `deploy.ps1`; параметры `-Ref`, `-Target`, `-Port`, `-TaskName` меняют ref,
каталог, порт и задачу. Поставленная так панель обновляется кнопкой, как любая, — готовой сборкой своего канала.

Поставленная панель собрана из master и правок ветки задачи не содержит: приёмку смотрят на dev-панели.

### На другом компьютере

Панель ставят одной строкой в Windows PowerShell:

```powershell
iex ((irm https://raw.githubusercontent.com/t8nax/agents-kit-web/master/scripts/install.ps1).TrimStart([char]0xFEFF))
```

`scripts/install.ps1` сначала проверяет, что на компьютере есть Claude Code со входом в аккаунт; нет — называет, что
сделать, и больше ничего не делает. Затем ставит через winget git и PowerShell 7, если их нет (Windows может спросить
разрешение), ставит кит из магазина плагинов Claude Code, если кита нет, скачивает готовую сборку последнего выпуска канала и ставит её `deploy.ps1`
из сборки. Список баз и путь к киту не переносятся — их задают в «Настройках» на месте. Параметры `-Releases`,
`-Channel`, `-Tag`, `-Target`, `-Port`, `-TaskName` — для запуска файлом.

## Песочница

Чтобы ломать панель, не задевая живые базы, есть одноразовая песочница: выдуманные базы и копии, заглушки
кита и агента, свой каталог и порт у каждой рабочей копии. Собирается под задачу: в неё кладутся только
названные куски — здоровый проект, каждая нарочно сломанная база отдельно — и свой кусок задачи, если
нужного случая в готовых нет. Без кусков сборка отказывает и перечисляет их.

```powershell
pwsh -NoProfile -File scripts/sandbox.ps1 -Pieces house,quirks
pwsh -NoProfile -File scripts/sandbox.ps1 -Pieces house -TaskPiece <путь к своему куску .ps1 вне репозитория>
```

Куски: `house` — здоровый проект, `orders` — свои буквы номеров, `tracker` — проекты с трекером, `no-product`, `broken-json`, `old-format`, `stages-only`,
`no-flow`, `quirks` — сломанные базы, `new-format` — база нового формата кита, `broken-kit` — кит без скриптов, `load` — полсотни копий.

Какие куски бывают, как дописать свой, что в них сломано заранее и как переключать режимы заглушек —
`scripts/sandbox.md`.

## Проверки

Полный прогон идёт на GitHub, а не на машине: его запускает отправка любой ветки, кроме dev и master
(`.github/workflows/checks.yml`), — тесты бэкенда, линт, тесты и сборка фронта, e2e, тремя машинами разом.
Ветку задачи сливают в dev, когда прогон её последнего коммита зелёный. Покраснела только проверка, записанная
в бэклоге как мигающая, — прогон перезапускают один раз (`gh run rerun <номер>`); снова красный — это поломка.

```sh
gh run watch <номер> --exit-status        # дождаться; номер — gh run list --branch <ветка>
gh run view <номер> --log-failed          # упавшее
gh run download <номер> -n e2e-failures   # след и снимок страницы упавших e2e
```

У себя, пока правят код, гоняют только сборку, линт и тесты тронутой части; e2e — только чтобы
воспроизвести упавшее на GitHub.

```sh
# бэкенд: тесты тронутых классов
cd backend
dotnet test --filter "FullyQualifiedName~<Класс>Tests"

# фронтенд
cd frontend
npm run lint
npx vitest related --run <тронутые файлы>
npm run build

# e2e: каждый прогон поднимает свои API и dev-сервер на свободных портах, запущенные не берёт
npx playwright install chromium   # один раз
npx playwright test <файл>
```
